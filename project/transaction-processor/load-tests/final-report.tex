\section{Problem, Team, and Overview of Experiments}

This project builds a distributed financial transaction processor that accepts transfer requests at an API layer, places work on a queue, and applies balance updates asynchronously. The core requirement is correctness under concurrency: the system must not lose money, apply a transfer twice, or produce inconsistent balances under retries or failures. The primary stakeholders are engineers building payment-style backends, operators responsible for reliability, and end users who expect transfers to remain correct under load.

Sampath Pranay Beela focuses on API design, service integration, load generation, and analysis. Rahul Chinya Jagadeesha focuses on DynamoDB schema design, worker-side concurrency control, correctness verification, and infrastructure automation.

The architecture uses a Go-based \texttt{api-svc}, a Go-based \texttt{worker-svc}, an SQS-compatible queue, and DynamoDB as the system of record. Transfers are recorded as \texttt{PENDING}, enqueued, and completed by the worker using conditional writes on account versions. Observability includes a health endpoint, transaction status records, service logs, Locust exports, and a balance reconciliation script. The planned cloud deployment extends this with CloudWatch logs and metrics.

The experimental plan has four parts: hot-account contention, worker crash recovery, optimistic versus pessimistic locking, and horizontal scaling. The main outputs are throughput, p95 latency, retry behavior, failure rate, and final balance correctness.

AI is used as a productivity tool for scaffolding, drafting, and initial code generation, but not as the final authority on correctness. Human review remains necessary for experiment design, debugging, and interpreting tradeoffs.

\section{Architecture}

The current Milestone 1 system runs fully locally. A user or Locust client sends a transfer request to \texttt{api-svc} on \texttt{localhost:8080}. The API validates the request, checks idempotency, writes a \texttt{PENDING} transaction record to DynamoDB Local, and sends the transfer message to the ElasticMQ queue. The \texttt{worker-svc} polls that queue, reads the sender and receiver accounts from DynamoDB Local, checks sufficient funds, performs debit and credit updates using optimistic locking, and then updates the transaction record to \texttt{COMPLETED} or \texttt{FAILED}. After load tests, \texttt{verify\_balances.py} scans DynamoDB Local to confirm that the total balance in the system is still correct.

The current local flow can be summarized with the following Mermaid diagram:

\begin{verbatim}
flowchart TD
    U[User / Locust Load Test] --> API[api-svc on localhost:8080]
    API --> CHECK[Validate request and check idempotency]
    CHECK --> TX1[Write PENDING transaction to DynamoDB Local]
    TX1 --> Q[Send message to ElasticMQ queue]

    Q --> W[worker-svc polls queue]
    W --> ACC1[Read sender account from DynamoDB Local]
    ACC1 --> FUNDS{Sufficient funds?}

    FUNDS -->|No| FAIL[Mark transaction FAILED]
    FUNDS -->|Yes| DEBIT[Debit sender with optimistic locking]
    DEBIT --> ACC2[Read receiver account]
    ACC2 --> CREDIT[Credit receiver with optimistic locking]
    CREDIT --> DONE[Mark transaction COMPLETED]

    FAIL --> TX2[Update transaction record in DynamoDB Local]
    DONE --> TX2

    API --> STATUS[GET transfer status]
    STATUS --> TX2

    V[verify_balances.py] --> DB[(DynamoDB Local)]
    TX1 --> DB
    TX2 --> DB
    ACC1 --> DB
    ACC2 --> DB
\end{verbatim}

\section{Objectives}

The short-term objective is to deliver a transaction processor that enforces three invariants: idempotent transfers, globally conserved balances, and no double spending under retries. A second short-term objective is to quantify how optimistic locking behaves under both mixed traffic and concentrated contention. A third is to make the system observable enough that correctness bugs are diagnosable rather than speculative.

The long-term objective is to evolve the system into a reusable benchmark for correctness-versus-throughput tradeoffs in financial write-heavy workloads. Future work includes richer failure injection, dead-letter queue analysis, request tracing, cloud-native observability, and a second coordination strategy for side-by-side comparison. More broadly, the project aims to answer when an eventually retried optimistic design is good enough and when stronger coordination is worth the cost.

This project sits in the same design space as course topics on asynchronous messaging, at-least-once delivery, optimistic concurrency control, and the cost of distributed coordination. The queue-backed design decouples bursty request ingestion from balance mutation, while DynamoDB conditional writes represent the optimistic-concurrency approach the experiments are meant to evaluate.

\section{Methodology}

The implementation follows a queue-backed asynchronous model. The API service validates requests, checks whether the transaction already exists, records a \texttt{PENDING} transaction with a conditional write, and enqueues the request. The worker polls the queue, reads the sender account, verifies funds, performs a version-checked debit, credits the receiver, and marks the transaction \texttt{COMPLETED}. Version conflicts trigger up to three retries with exponential backoff. Non-recoverable conditions such as missing accounts or insufficient funds mark the transaction \texttt{FAILED}.

This design exposes the main tradeoff the project studies. Optimistic locking keeps the steady-state fast because no distributed lock service is involved, but it pushes complexity into retries when many writers target the same item. The worst-case workload is therefore a hot-account storm, while the base case is a mixed workload over many accounts.

Observability is built into the method. API responses expose transfer status, worker logs show retry behavior, Locust exports latency and throughput histories, and the verifier scans the accounts table to ensure that the seeded total balance of \$1{,}010{,}000 is preserved to within a one-cent tolerance. The experiments are incremental: the system must pass the smoke test and preserve balances before any comparative performance claims are made. AI use within the methodology is intentionally narrow; generated code and documentation are still checked against measured behavior.

Two findings stand out. First, the system sustained 270.84 requests/s in the mixed run and 380.38 requests/s in the hot-account-only run while keeping request-level failure rate at 0\%. Second, the hot-account-only scenario did not cause the dramatic latency collapse that an optimistic-locking design might fear at this scale; its p95 latency was 7 ms, better than the 10 ms aggregated p95 in the mixed run. The history files show that the hot-account scenario reached 394.7 requests/s at peak while the mixed run peaked at 280.7 requests/s. This suggests that, at 50 concurrent users and with the current retry budget, the implementation absorbs conditional-write conflicts without surfacing instability to the client.

The mixed-run breakdown is also informative. Of the 81{,}152 total requests in the mixed scenario, 56{,}916 came from the hot-transfer workload and 24{,}236 came from random transfers. Despite this blend of low- and high-contention paths, the average latency remained only 4.32 ms and the p99 remained 32 ms.

The hot-account-only run is the strongest preliminary result because it tests the case that should hurt optimistic concurrency the most. It completed 113{,}950 requests with a median latency of 2 ms, average latency of 3.86 ms, and p99 of 28 ms while still reporting zero failures. This does not prove that optimistic locking will remain superior at higher concurrency, but it does establish that the current implementation is stable at the 50-user stress level.

The error artifacts reinforce that interpretation. Both failure CSV files contain no failure rows, and both exception CSV files are empty. That means the local system produced zero request-level failures and zero recorded exceptions across both runs. This should not be overinterpreted as proof of general robustness, but it is useful evidence that the prototype is stable enough for larger experiments.

The current results are still preliminary because only the local mixed-load and hot-account experiments have been completed. Worker crash recovery, optimistic-versus-pessimistic comparison, and horizontal scaling remain future work.

\section{Impact}

This project matters because it turns a common distributed-systems claim, ``eventual correctness under retries,'' into something measurable for a write-heavy financial workload. Engineers can use the system and experiments to reason about when conditional writes are sufficient, when stronger coordination is worth the overhead, and how much observability is needed before trusting a queue-backed money movement pipeline.

The broader significance is practical. Many distributed applications can hide small inconsistencies behind caching or reconciliation, but a financial transaction processor cannot. A clear comparison among optimistic locking, failure recovery, and scaling can inform the design of payment services, wallet backends, or approval systems where correctness violations have direct business cost.
